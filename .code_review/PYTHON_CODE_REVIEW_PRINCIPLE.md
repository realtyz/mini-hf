# 代码审查原则

## 一、设计原则

### 1. SOLID 原则

#### 单一职责原则 (SRP)

每个类/函数只应有一个引起变化的原因。

- **审查要点**：一个类是否同时处理业务逻辑、数据库访问、网络请求？函数是否"做了一件以上的事"（可通过函数名中的 `and`/`or` 嗅探）？

#### 开闭原则 (OCP)

对扩展开放，对修改关闭。

- **审查要点**：新增功能时是否需要大量修改原有类？是否通过抽象（`ABC`/`Protocol`）和多态扩展，而非到处添加 `if-elif-else`？

#### 里氏替换原则 (LSP)

子类应当能够替换父类而不破坏程序正确性。

- **审查要点**：子类是否抛出了父类未声明的异常？是否改变了方法签名预期行为（如返回类型不兼容、违反约定）？可检查 `isinstance` 滥用。

#### 接口隔离原则 (ISP)

不应强迫客户端依赖它们不使用的方法。

- **审查要点**：是否存在"胖接口"（一个 `ABC` 拥有过多抽象方法）？客户端是否只依赖需要的协议？可用 `Protocol` 或小接口拆分。

#### 依赖倒置原则 (DIP)

高层模块不应依赖低层模块，两者都应依赖抽象。

- **审查要点**：高层业务类是否直接导入并具体使用底层库/模块？是否依赖注入或通过抽象解耦？可检查 `from sqlalchemy.orm import Session` 是否直接硬编码在业务服务中。

### 2. KISS (Keep It Simple, Stupid)

保持实现简单直白，避免不必要的复杂度。

- **审查要点**：是否存在过度工程化设计模式（为未来扩展而加的抽象）、非必要的元类、多层装饰器嵌套？简单循环能完成的是否用了复杂的函数式/生成器魔力？

### 3. DRY (Don't Repeat Yourself)

避免重复代码和重复逻辑，每个知识点在系统中应只有单一明确表示。

- **审查要点**：是否存在重复的校验逻辑、配置读取、相似的函数体？可抽取为公共函数/工具类/装饰器。但注意勿"滥用 DRY"（若两个巧合相似的函数将来会独立变化，强行合并会违反 SRP）。

### 4. YAGNI (You Aren't Gonna Need It)

不要提前实现当前不需要的功能。

- **审查要点**：是否有为"将来可能"预留的参数、配置项、抽象接口？审查时应移除未使用的代码路径。

### 5. 组合优于继承

通过组合对象来获得行为，而非深层的继承体系。

- **审查要点**：是否存在多层的类继承？是否能用依赖注入替换继承？Python 的 Mixin 虽方便但应谨慎检查命名冲突。

### 6. 关注分离 (Separation of Concerns)

各部分代码应专注于各自领域，例如业务逻辑不与展示/存储混杂。

- **审查要点**：视图函数中是否有直接的 SQL 查询或 ORM 遍历？业务服务是否混入了请求对象或响应格式？

## 二、可读性与一致性

- **命名**：变量、函数、类命名是否见名知义？遵守 PEP 8（`snake_case` 用于变量/函数，`PascalCase` 用于类）。
- **函数长度与参数**：函数是否过长（通常 >20-30 行需警惕）？参数是否过多（>3-4 个考虑封装为数据类）？
- **注释与文档字符串**：公开 API 是否有 docstring（Google/NumPy/Sphinx 风格）？注释解释的是"为何如此"而非"做了什么"。
- **魔法数字与字符串**：是否定义了常量或枚举来替换赤裸的数字/字符串？
- **import 规范**：标准库、第三方库、本地模块分组，按字母顺序排列，无未使用的导入。
- **类型注解**：关键函数/方法是否有类型注解，以辅助理解和静态检查。

## 三、Python 特性和陷阱

- **可变默认参数**：避免 `def func(lst=[])`，应使用 `None` 默认。
- **列表推导与生成器**：用于大数据集时是否考虑生成器表达式节省内存？列表推导不应有副作用。
- **异常处理**：是否捕获过于宽泛的 `except Exception` 或裸 `except:`？是否可能吞掉关键异常？`finally` 块用于资源释放（或使用 `with`）。
- **上下文管理器**：文件、网络、锁等是否使用 `with` 语句？
- **资源管理**：是否显式关闭连接、文件？建议使用 `with` 或设置 `__del__` 但后者不可靠。
- **可变与不可变类型**：是否错误地修改了可变对象传递导致的副作用？函数是否返回了内部可变对象的引用破坏封装？
- **类变量与实例变量**：检查类属性（尤其是列表、字典）被意外共享的风险。
- **`__init__` 外定义属性**：建议所有实例属性在 `__init__` 中初始化，避免出现时有时无的 `AttributeError`。
- **使用 `is` 和 `==`**：与 `None`、`True`、`False` 比较使用 `is`，而非 `==`。
- **f-string vs `.format()`**：Python 3.6+ 优先使用可读性好的 f-string。

## 四、异步编程专项

- **事件循环阻塞**：async 函数中是否调用了同步阻塞 IO（如 `requests`、`time.sleep`、同步文件读写）？应替换为 `aiohttp`/`httpx`、`asyncio.sleep`、`aiofiles` 或使用 `asyncio.to_thread()` 委托至线程池。
- **取消处理**：`CancelledError` 是否被正确传播？是否存在 `except Exception` 吞掉取消信号导致任务无法终止的情况？需要清理资源时应捕获 `CancelledError` 执行清理后 `raise`。
- **并发策略**：`asyncio.gather` 是否正确选择错误策略？默认任一失败即抛异常，是否应使用 `return_exceptions=True` 收集全部结果后再统一处理？
- **异步上下文管理器**：异步资源（数据库 session、网络连接、锁）是否使用 `async with` 确保释放？是否存在 `await` 路径上遗漏 `await` 导致协程未执行？
- **竞争条件**：多个协程并发访问共享状态时是否使用 `asyncio.Lock` 保护？是否存在 `await` 点之间的检查-使用（TOCTOU）竞态？
- **背压与并发控制**：是否使用 `asyncio.Semaphore` 或队列限制并发数？无限制的 `gather` 可能导致资源耗尽。

## 五、数据库与迁移

- **事务边界**：事务范围是否清晰？避免事务跨越多个不相关的业务操作。写操作是否在事务内？只读查询是否使用只读事务或合适的隔离级别？
- **Session 生命周期**：异步 session 是否正确使用 `async with` 管理？是否存在 session 泄露（未关闭）或跨请求复用 session 的情况？
- **N+1 查询**：是否存在循环内逐条查询关联数据？应使用 SQLAlchemy 的 `selectinload`/`joinedload`/`subqueryload` 预加载关联对象，或手动批量查询。
- **批量操作**：大批量插入/更新是否使用了批量操作（`bulk_insert_mappings`、`execute(update(...))`）而非逐条 ORM 操作？
- **迁移安全性**：Alembic 迁移是否可逆（`downgrade` 实现）？对大表加列/加索引是否使用 `CREATE INDEX CONCURRENTLY` 等非阻塞方式？数据迁移是否包含回滚数据的安全策略？
- **并发任务领取**：Worker 从数据库领取任务时是否使用原子操作（如 `UPDATE ... WHERE status = 'PENDING' RETURNING ...`）防止竞态条件？是否使用乐观锁（版本号）或 `SELECT FOR UPDATE` 保护并发修改？

## 六、API 设计一致性

- **错误响应格式**：错误响应是否统一（包含 `error_code` + `message` 结构）？HTTP 状态码是否语义正确（如 409 用于冲突、422 用于校验失败）？
- **分页参数**：分页接口参数是否一致（`mgmt_server` 使用 `skip`/`limit` 形式进行分页）？是否包含总数信息？
- **幂等性**：任务提交等写操作接口是否考虑幂等性？重复请求是否会创建重复资源？是否使用幂等键或唯一约束防护？
- **版本管理**：API 路径是否包含版本号（`/api/v1/`）？破坏性变更是否通过版本升级而非原地修改？
- **输入校验**：是否使用 Pydantic model 对请求体做严格校验？路径参数和查询参数是否有边界检查？

## 七、分布式系统健壮性

- **重试与退避**：外部服务调用（S3、HuggingFace API、Redis）是否实现重试？是否使用指数退避（exponential backoff）避免雪崩？是否区分可重试错误（网络超时）和不可重试错误（认证失败）？
- **级联失败**：依赖服务不可用时是否有兜底策略（降级、缓存兜底、熔断）？是否会因为下游慢导致上游连接池耗尽？
- **任务状态一致性**：Worker 崩溃时任务是否停留在 `RUNNING` 状态成为僵尸任务？是否有超时检测或心跳机制回收？
- **优雅退出**：Worker 接收到终止信号时是否完成当前任务后再退出？是否有优雅关闭流程（`signal`/`lifespan`）？
- **幂等执行**：任务重试时是否幂等？部分完成的操作（如已上传部分文件到 S3）重试时是否能正确恢复而非重复执行？

## 八、错误处理与健壮性

- 是否对输入参数进行校验并快速失败（fail fast）？
- 异常是否链式传播（`raise ... from ...`）以保留上下文？
- 日志记录是否适当（`DEBUG`, `INFO`, `WARNING`, `ERROR`），无敏感信息？
- 外部依赖（API、数据库）调用是否有超时/重试机制？
- 是否处理了 `KeyboardInterrupt` 或系统信号以做优雅退出？

## 九、性能考量

- 循环内是否有重复的计算、不必要的属性访问或数据库查询（N+1）？
- 是否使用了合适的数据结构（`set`/`dict` 用于查找，`deque` 用于队列等）？
- 是否避免在循环中拼接字符串？可使用 `''.join()`。
- 大对象是否及时释放？是否有循环引用导致内存泄漏？
- 异步代码中是否阻塞了事件循环（如 `time.sleep` 应改为 `asyncio.sleep`，同步 IO 应在线程池执行）？

## 十、安全

- SQL 查询是否使用参数化，避免拼接注入。
- 命令行执行是否存在 shell 注入（`subprocess` 避免 `shell=True` 且参数列表化）。
- 用户输入是否进行校验和转义（XSS、路径遍历等）。
- 敏感信息（密钥、密码）是否硬编码？应从环境变量或安全存储读取。
- 反序列化（`pickle`）是否可信？避免加载不可信数据。
- 依赖项是否有已知漏洞（使用工具扫描）？

## 十一、测试与可测试性

- 是否有针对关键业务逻辑的单元测试？边缘情况是否覆盖？
- 代码是否易于测试（依赖注入、无隐式全局状态）？
- 测试是否独立、可重复？是否有随机性未设置种子？
- Mock 是否过度使用，导致测试与实现紧密耦合？

## 十二、项目结构与管理

- 项目目录结构是否清晰（如 `src/`, `tests/`, `config/`）？
- 依赖项是否明确记录（`requirements.txt` 或 `pyproject.toml`）并带有版本约束？
- 配置文件与代码是否分离，敏感配置不提交至仓库？
- `.gitignore` 是否忽略虚拟环境、缓存、编译产物等？
- README 是否包含安装、运行、测试说明。

## 十三、审查分级

审查意见应区分严重程度，避免所有 comment 同等对待导致重要问题被淹没。

### Blocking（必须修复，阻塞合并）

- 安全漏洞（SQL 注入、硬编码密钥、路径遍历）
- 数据丢失风险（迁移不可逆、删除操作无确认）
- 生产故障风险（竞争条件导致数据不一致、资源泄露、死锁）
- 逻辑错误导致功能不可用

### Suggestive（建议改进，不阻塞合并）

- 性能优化（N+1 查询、可优化为批量操作）
- 代码风格与可读性（命名、过长函数、缺失类型注解）
- 设计改进（违反 SOLID 原则、可简化的抽象）
- 测试补充（缺少边缘情况覆盖）
